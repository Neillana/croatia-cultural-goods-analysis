Open-Data-Portal Kroatien

Author

Sonja K. Bauer

Auf European data wird als Quelle für das kroatische Register für Kulturgüter das Open Data Portal Kroatien angegeben. Öffnet man den Link, findet man dort die Adresse des Portals https://data.gov.hr/.

Recherchiert man dagegen bei Google und folgt direkt dem ersten Ergebnis “Portal otvorenih podataka”, weigern sich Firefox und Bitdefender die Seite aufzurufen, da dort die Adresse https://www.data.gov.hr hinterlegt ist und dafür kein Zertifikat vorhanden ist. Man muss das “www” aus der Adresse manuell entfernen.

CautionFirefox: Warum sieht die Website gefährlich aus?

Die Website wurde so eingerichtet, dass sie nur sichere Verbindungen zulässt. Es gibt jedoch ein Problem mit dem Zertifikat der Website. Es ist möglich, dass jemand Böswilliges versucht, sich als die Website auszugeben. Websites verwenden Zertifikate, die von einer Zertifizierungsstelle ausgestellt wurden, um zu bestätigen, dass sie wirklich sind, für wen sie sich ausgeben. Firefox vertraut dieser Website nicht, weil das Zertifikat nicht für www.data.gov.hr gilt. Das Zertifikat ist nur gültig für: gov.hr, *.gov.hr. Was können Sie dagegen tun?

www.data.gov.hr verwendet eine Sicherheitstechnologie namens “HTTP Strict Transport Security (HSTS)”, durch welche Firefox nur über gesicherte Verbindungen mit der Website verbinden darf. Daher kann keine Ausnahme für die Website hinzugefügt werden.

Das staatliche Open Data Portal und der Datensatz im besonderen weisen eine Reihe von Nutzungsbarrieren für internationale Nutzer auf.

Sprachbarriere

Obwohl in der Seitennavigation die Option zur Verfügung steht, die Sprache auf Englisch umzustellen, verbleiben die meisten Inhalte auf Kroatisch. Die einzige Möglichkeit ist, die Übersetzungsfunktion des Browsers zu verwenden. Beim Umstellen der Sprache wird der Browser allerdings direkt auf die Startseite umgeleitet, so dass man den Datensatz erneut aufrufen muss.

Lizenz

Die Lizenz des Datasets ist in der kroatischen Form angegeben: Otvorena dozvola (OD) Es handelt sich nicht um eine CC-Lizenz, sondern um eine spezifische, staatliche Open-Data-Lizenz für Informationen des öffentlichen Sektors in Kroatien. Folgt man dem Link wird dies deutlich, denn die Lizenz wird lediglich als Open licence bezeichnet. Dies ist im Rahmen der EU-Richtlinie zwar zulässig, entspricht aber nicht dem Open-Data-Standard, für den vorzugsweise eine CC-Lizenz vorhanden sein sollte.

Metadaten

Die Metadaten bestehen aus einen Mix von kroatischen und englischen Angaben. Eine Option zum Download der Metadaten oder den Hinweis zu einer entsprechenden API sucht man vergeblich.

Um herauszufinden, wie die Metadaten heruntergeladen werden können, bin ich in der Navigation Knowledge base dem Link zu Resources for development engineers gefolgt. Man wird zu einem eingebetteten moodle-Kurs weitergeleitet und erhält eine komplett kroatische Anzeige, obwohl die Sprachauswahl auf Englisch eingestellt bleibt. Wenn man kroatisch nicht versteht, bleibt also wieder nur die Nutzung des Browsertools. Beim Abschnitt über die Abfrage von Metadaten zeigt der Browser auf einmal Serbisch statt Kroatisch als Seitensprache an.

CKAN-API

def fetch_ckan_metadata(api_url: str) -> pd.DataFrame:
    """Fetch and flatten CKAN metadata from a JSON API endpoint.

    Reads the JSON response from the given CKAN API URL using DuckDB,
    extracts all keys and values from the `result` object, and returns
    them as a long-format DataFrame with one row per metadata field.
    Empty or missing values are replaced with "keine Angabe".

    Args:
        api_url: URL of the CKAN API endpoint returning a JSON object
            with a top-level `result` field.

    Returns:
        DataFrame with columns `metadata_field` and `value`.

    Raises:
        duckdb.Error: If the query execution or JSON parsing fails.
    """
    with duckdb.connect(database=":memory:") as con:
        query = f"""
            WITH raw_data AS (
                SELECT * FROM read_json_auto('{api_url}', maximum_object_size=10485760)
            ),
            keys_extracted AS (
                SELECT unnest(json_keys(result)) AS field_key
                FROM raw_data
            ),
            key_value_pairs AS (
                SELECT
                    k.field_key AS metadata_field,
                    CAST(r.result->>k.field_key AS VARCHAR) AS raw_val
                FROM raw_data r, keys_extracted k
            )
            SELECT
                metadata_field,
                COALESCE(NULLIF(raw_val, ''), 'missing') AS value
            FROM key_value_pairs
        """

        try:
            return con.sql(query).df()
        except duckdb.Error as e:
            logger.critical(
                f"Critical error retrieving data from {api_url}: {e}"
            )
            raise

Lizenzdaten

Der Wert access_rights ist auf public gesetzt. Gleichzeitig suggeriert der Wert isopen:'false', dass der Datensatz nicht öffentlich zugänglich ist. Dies lässt sich darauf zurückführen, dass das System (CKAN) die kroatische Lizenz nicht als offen erkennt.

Direkt danach wird angegeben: license_id:'open-licence'. Des Weiteren wird als Lizenz mit license_title: 'Otvorena dozvola (OD)' (“offene Lizenz”) eine nationale kroatische Lizenz angezeigt. Ruft man die Lizenz auf, stößt man abermals auf eine Sprachbarriere, da es keine englische Übersetzung gibt.

Europäische Rechtsgrundlage

Für applicable_legislation ist http://data.europa.eu/eli/reg_impl/2023/138/oj angegeben. Es handelt sich um die “Durchführungsverordnung (EU) 2023/138 der Kommission vom 21. Dezember 2022 zur Festlegung bestimmter hochwertiger Datensätze und der Modalitäten ihrer Veröffentlichung und Weiterverwendung (Text von Bedeutung für den EWR)”. Laut Rechtsgrundlage und laut Angabe im Feld hvd_category: http://data.europa.eu/bna/c_6c2bb82d gehören die Daten des Registers zur Datenkategorie 1) Georaum, da es sich um Schutzgebiete handelt und sind als “high-value dataset” klassifiziert. Folgt man dem Link erhält man <skos:prefLabel xml:lang="en">Geographical names</skos:prefLabel>. Der Wert is_hdv: 1 bestätigt dies zusätzlich. Die vorliegenden Daten enthalten aber keinerlei Geodaten, wie wir noch sehen werden.

Autor

Der Wert autor: Služba za javnu komunikaciju Ministarstva teilt mit, dass es sich um das “Amt für öffentliche Kommunikation des Ministeriums” handelt, gibt aber nicht den Namen des Ministeriums an. Es muss aus dem Wert author_email: marija.siskoomrcen@min-kulture.hr erschlossen werden, dass es sich um das Ministerium für Kultur und Medien handelt. Auch ist hier die Email eines konkreten Mitarbeiters hinterlegt, der natürlich wechseln kann.

Nationale Rechtsgrundlage

Im Feld conforms_to werden die nationalen Rechtsgrundlagen aufgeführt.

Koordinator und Maintainer

Die Werte für coordinator und coordinator_email fehlen, das gleiche gilt für maintainer und maintainer_email.

Aktualisierungsrate

Obwohl data_refresh_frequency: daily angegeben wird, bleibt die tatsächliche Aktualisierung offen. Der Wert von metadata_modified ändert sich täglich (doch die Metadaten verändern sich seit meiner Recherche nicht) und der Wert resources: [{"cache_last_updated":null,"cache_url":null,"... sagt aus, dass die Dateien nicht auf dem CKAN-Server gespiegelt werden, man greift also direkt auf den Original-Server der Behörde zu. Da kein Cache vorhanden ist, gibt es auch keine URL dazu.

Statistische Daten

Der Wert includes_statistical_data: True suggeriert das Vorhandensein von statistischen Daten. Wie wir sehen werden, sind aber keine statistischen Daten vorhanden. Es handelt sich im Grunde genommen um eine Inventarliste. Verursacht wird dieser Wert vermutlich durch die falsche Zuordnung zum Thema “Bevölkerung und Gesellschaft”, bei dem es sich tasächlich um statistische Daten handelt.

Themen-Zuordnung

Während der Datensatz auf EU-Ebene im Rahmen der High-value datasets der Kategorie Geographical names zugeordnet wird, ordnet das kroatische Portal diesen mit theme:'population_and_society' einem anderem, statistischen Thema zu.

URL

Dataset-URL (Landing Page / url): Der eigentliche Permalink zur Website des Portals, auf der dieser Datensatz mit seiner Beschreibung visualisiert wird (z. B. https://data.gov.hr/dataset/…). Beim Anlegen des Eintrags in CKAN wurde keine offizielle Quell-URL oder Landingpage hinterlegt. Man kann zwar die Datei herunterladen, aber den redaktionellen Ursprung im Portal nicht direkt über eine stabile Web-Adresse verlinken (Permalink).

Version

Fehlende Versionskontrolle: Open-Data-Richtlinien (und insbesondere FAIR-Prinzipien) fordern klare Versionsangaben für Datensätze, die sich regelmäßig ändern. Wenn die Version fehlt, weiß ein automatisierter ETL-Prozess oder ein Endnutzer nicht, ob es sich um den Stand von 2023, 2026 oder eine ungetestete Zwischenversion handelt. Man kann sich hier nur mühsam auf den last_modified-Zeitstempel der Ressource verlassen.

Resources

Fehlende Beschreibungen: Während das CSV- und XML-Feld für description einen leeren String "" enthalten, ist das JSON-Feld explizit null. Es gibt auf Ressourcenebene keinerlei textliche Dokumentation darüber, welche Spalten konkret enthalten sind oder wie das Schema aufgebaut ist.

Tags Die Tags stammen direkt aus dem kroatischen Denkmalschutzrecht und unterteilen das Register in drei Hauptkategorien sowie einen Oberbegriff:

  • kulturna baština (Kulturerbe): Der übergeordnete Dachbegriff für das gesamte Themenfeld.
  • kulturno dobro (Kulturgut): Die generelle Bezeichnung für ein geschütztes Objekt.
  • nepokretno kulturno dobro (Unbewegliches Kulturgut): Architektur, Denkmäler, historische Gebäude, archäologische Stätten oder historische Gärten/Parks.
  • nematerijalno kulturno dobro (Immaterielles Kulturgut): Traditionen, Bräuche, Handwerkskünste, mündliche Überlieferungen oder darstellende Künste (gemäß UNESCO-Konvention).

Die Bedeutung von vocabulary_id: null

In CKAN bedeutet ein Wert von null für das Feld vocabulary_id, dass es sich um freie (unkontrollierte) Tags handelt, die direkt von den Erstellern beim Hochladen vergeben wurden, anstatt aus einem zentralen, standardisierten Vokabular (einer kontrollierten Taxonomie oder einem Thesaurus) zu stammen.

  • Kein semantisches Netz / Ontologie: Das bedeutet, dass das Portal diese Begriffe nicht automatisch mit übergeordneten Normdaten (wie Wikidata, Eurovoc oder europäischen Thesauri) verknüpft. Sie existieren nur als reine Text-Schlagworte auf dem Datensatz.
  • Keine Hierarchie auf API-Ebene: Obwohl fachlich eine Logik existiert (z. B. dass nepokretno kulturno dobro eine Unterart von kulturno dobro ist), weiß das CKAN-System das strukturell nicht. Für das System sind das einfach vier voneinander unabhängige Strings.

Für eine saubere Datenanalyse oder den Import in ein semantisches Web-Modell (RDF/OWL) bedeutet dies, dass man diese flachen Strings selbst in eine saubere Klassenhierarchie überführen muss, da das Portal sie rein als unstrukturierte Freitext-Schlagworte liefert.

Die Metadaten der Ressource zeigen, dass es sich nicht um einen echten API-Endpunkt handelt, sondern um hochgeladene Dateien. Direkte Abfragen unter verwendung von z.B. SQL sind nicht möglich, da:

  • die Ressource über url_type: “upload” verfügt,
  • der DataStore deaktiviert ist (datastore_active: false),

Die Aktualisierung der Dateien erfolgt zwar täglich, wie die Werte von last_modified und metadata_modified zeigen das Fehlen von Cache-Mechanismen cache_last_updated: "missing" und eines Hashes hash: missing. Das lässt keinen Rückschluss darauf zu, ob sich tatsächlich Daten geändert haben.

Zudem existiert kein festes Schema für die Dateien:

  • Struktur (Spaltennamen, -anzahl, Datentypen) kann sich bei jedem Upload ändern.
  • keine Schema-Validierung oder Dokumentation der Felder.

Folgen:

  • Keine automatisierte Verarbeitung möglich, da die Datenstruktur potentiell instabil ist.
  • Die Struktur muss vor jeder Analyse geprüft und ggf. manuell angepasst werden.
  • Durch den fehlenden Hash (hash: “missing”) kann keine inhaltliche Veränderung der Datei nachvollzogen werden.

Untersuchung des Updateverlaufs

Das Dataset verfügt über einen Tab Activity Stream. Dieser zeigt, dass jeden Abend um ca. 19:20 Uhr drei Cronjobs angestoßen werden, offenbar ein Cronjob für jede der drei Dateien (JSON, XML, CSV). Erste Datensichtung und Strukturanalyse

Noch vor einem Download der Daten lässt sich für die Formate JSON, XML und CSV über die Schaltfläche Explore ein Preview öffnen, das Preview für das Format CSV kann allerdings nicht angezeigt werden.

  • Spaltennamen beginnen mit einem Großbuchstaben und nutzen Unterstriche zur Trennung
  • Spaltennamen sind ausschließlich auf Kroatisch vorhanden
  • Datenwerte sind nicht bereinigt: führende Leerzeichen und Excel-Artefakte am Ende von Werten: \n\r
  • Keine maschinenverwertbare Normalisierung der Daten
  • Emails von Mitarbeitern örtlicher Museen mir vollem Namen
  • Telefonnummern und Handynummern von Mitarbeitern örtlicher Museen

Zwischenfazit

In den Metadaten finden sich keine Angaben zur Datenquelle (resources). Die Inspektion der ausgelieferten Daten legt allerdings den Schluss nahe, dass es sich nicht um den Export aus einem normalisierten Datenbanksystem handelt, sondern um eine automatisierte Konvertierung einer Excel-Tabelle des Ministeriums für Kultur und Medien. Speziell die vorliegenden Formatierungsartefakte zeigen, dass keinerlei Bereinigung der Daten stattgefunden hat. Für eine sinnvolle Weiterverwendung ist daher ein vorgelagerter Schritt zur Bereinigung und Normalisierung unerlässlich.

Für eine automatisierte Abfrage der Daten über die CKAN-API ist der Datensatz nicht geeignet, da die Daten lediglich als Datei abgelegt und nicht in CKAN eingespeist werden. Da eine tatsächliche Änderung der Daten über die API nicht ersichtlich ist, müsste die gesamte Datei täglich heruntergeladen und auf Seiten des Empfängers geprüft werden. Es können nicht nur unvorhersagbar neue Daten enthalten sein, sondern auch unvorhersagbar eine Änderung der Spaltennamen und/oder Spaltenanzahl stattfinden. Dadurch entsteht ein in den meisten Fällen unnötiger Datenverkehr und die Notwendigkeit einer permanenten Überprüfung des Datenschemas.

def convert_latest_json_to_parquet(data_raw: Path) -> Path:
    """
    Convert the most recent JSON file in the given directory to a Parquet file.

    Searches the given directory for files matching the pattern
    "*_datagovhr_rkd.json", selects the (alphabetically/chronologically)
    latest file, and converts it into a Parquet file with the same
    filename (but with a .parquet extension) using DuckDB.

    Args:
        data_raw: Path to the directory containing the raw JSON data.

    Returns:
        Path to the generated Parquet file.

    Raises:
        FileNotFoundError: If no matching JSON files are found in the directory.
    """
    json_files = sorted(data_raw.glob("*_datagovhr_rkd.json"))
    if not json_files:
        raise FileNotFoundError("Keine passenden JSON-Dateien im Verzeichnis gefunden.")
    latest_json = json_files[-1]
    parquet_output = latest_json.with_suffix(".parquet")
    print(f"Aktuellste Datei: {latest_json.name}")
    with duckdb.connect() as con:
        con.execute(
            f"COPY (SELECT * FROM read_json_auto('{latest_json}')) TO '{parquet_output}' (FORMAT 'PARQUET')"
        )
    print("Konvertierung erfolgreich abgeschlossen.")
    print(f"Parquet-Datei: {parquet_output.name}\n")
    return parquet_output

def extract_metadata(df: pd.DataFrame) -> pd.DataFrame:
    """
    Build a summary table with metadata for each column of a DataFrame.

    For each column, this computes the data type, the number and percentage
    of missing values, the number and percentage of unique values, and,
    for string columns, the maximum string length, leading whitespace
    occurrences, and embedded newline occurrences.

    Args:
        df: The DataFrame to analyze.

    Returns:
        A DataFrame with one row per column of the input DataFrame and the
        computed metadata as columns, indexed by the original column
        position ("index").
    """
    total_rows = len(df)
    metadata = []
    for idx, col in enumerate(df.columns):
        dtype = df[col].dtype
        num_nan = df[col].isna().sum()
        num_unique = df[col].nunique()
        valid_rows = total_rows - num_nan
        pct_nan = (num_nan / total_rows) * 100
        pct_unique = (num_unique / valid_rows * 100) if valid_rows > 0 else 0.0

        max_str_len = None
        starts_with_whitespace = 0
        contains_newline = 0

        if pd.api.types.is_string_dtype(dtype) or dtype == 'object':
            col_as_str = df[col].astype(str)
            if num_nan < total_rows:
                max_str_len = df[col].str.len().max()
            starts_with_whitespace = col_as_str.str.match(r'^\s').sum()
            contains_newline = col_as_str.str.contains(r'[\r\n]').sum()

        metadata.append({
            "index": idx,
            "column_name": col,
            "type": str(dtype),
            "nan": num_nan,
            "nan_pct": f"{pct_nan:.1f}%",
            "uniques": num_unique,
            "uniques_pct": f"{pct_unique:.1f}%",
            "max_len": int(max_str_len) if pd.notna(max_str_len) else "-",
            "starts_whitespace": starts_with_whitespace,
            "contains_newline": contains_newline,
        })
    return pd.DataFrame(metadata).set_index("index")

Analytische Erkenntnisse der Erstinspektion

Die automatisierte Auswertung und deren visuelle Aufbereitung legen fundamentale strukturelle und qualitative Mängel im Datensatz offen:

  • Redundanzen in Registernummer: 4 Registernummern kommen mehrfach vor
  • Redundanzen in Textfeldern: Die Objektbezeichnungen (Naziv) und die detaillierten Beschreibungen (Opis_dobra) weisen Mehrfachnennungen auf.
  • Strukturelle Verunreinigungen: Die hohe Anzahl an Feldern mit führenden Whitespaces und Zeilenumbruch-Artefakten (\r\n) untermauert die Hypothese eines unbereinigten Excel-Exports. Eine automatisierte String-Bereinigung ist zwingend erforderlich.
  • Potenzial zur Kategoriengenerierung: Spalten mit einer geringen Anzahl eindeutiger Werte (z. B. Zupanija, Klasifikacija oder Pravni_status) eignen sich im weiteren Verlauf hervorragend für eine Transformation in den Datentyp Category, um den Speicherbedarf zu minimieren und spätere Aggregationen zu erleichtern.

  • Geodaten fehlen vollständig
